## Challenges and Growth Areas

### 1. Scope Creep in Code Reviews
**Issue:** Code reviews consistently added enhancements beyond original acceptance criteria

**Examples:**
- Story 2.4: Added dark mode support, improved loading skeletons, retry button in error states
- Story 2.3: Enhanced null handling, better documentation
- Story 2.2: Added error display and expiration date to invite UI

**Root Cause:** Lack of clear boundaries between "must fix" and "nice to have" in code review process

**Charlie (Senior Dev):** "Code review is becoming a 'polish everything' phase instead of 'catch critical issues' phase. We should be catching these during implementation, not in review."

**Impact:**
- Increased time to complete stories
- Blurred scope boundaries
- Inconsistent "done" definition

### 2. Recurring Pattern: Null Handling
**Issue:** Nullable fields require explicit handling but this keeps being missed in first implementation

**Evidence:**
- Story 2.3: Fixed null `full_name` handling in code review
- Pattern emerges across stories but not proactively addressed

**Elena (Junior Dev):** "The null handling and error states - those keep being 'nice to have' additions in review instead of being part of the original implementation."

### 3. Inconsistent Frontend Error States
**Issue:** No standard pattern for error handling across stories

**Evidence:**
- Story 2.1-2.3: Basic error handling only
- Story 2.4: Added retry button in error state during review

**Gap:** Should be a reusable pattern, not ad-hoc per story

### 4. Missing Retrospective Practice
**Issue:** Epic 1 retrospective was never completed, losing early learnings

**Bob (Scrum Master):** "We haven't been documenting learnings between epics. Epic 2's improvements were organic - we got better as we went, but without retrospectives, we're not consciously capturing those learnings."

**Impact:** Lost opportunity to build on Epic 1 learnings for Epic 2

## Action Items

### Process Improvements

#### 1. Define "Minimum Viable Story" Standard
- **Owner:** Charlie (Senior Dev)
- **Action:** Create a checklist of what EVERY story must include before submission for review
- **Items to include:**
  - Error states (with retry actions where applicable)
  - Loading states
  - Null handling for all nullable fields
  - Basic accessibility (keyboard navigation, ARIA labels)
  - Boundary condition testing
- **Success Criteria:** Dev agent references checklist before marking story ready for review
- **Deadline:** Before Epic 3 Story 3.2
- **Priority:** HIGH

#### 2. Clarify Code Review Scoping
- **Owner:** Bob (Scrum Master)
- **Action:** Define clear boundaries for code review severity levels
- **Definitions:**
  - **CRITICAL/HIGH:** AC violations, security issues, breaking changes (blocks completion)
  - **MEDIUM:** Best practices violations (fix if quick, defer if not, doesn't block)
  - **LOW/ENHANCEMENT:** Nice-to-haves (log to technical-debt.yaml, never block)
- **Success Criteria:** Code review outcomes follow this consistently starting with Epic 3
- **Deadline:** Immediate (apply to next story review)
- **Priority:** HIGH

#### 3. Mandate Retrospectives
- **Owner:** Product Owner + Scrum Master
- **Action:** Commit to running retrospectives after EVERY epic (not optional)
- **Scope:** Capture lessons learned, action items, and preparation needs
- **Success Criteria:** Epic 3 retrospective is completed before Epic 4 starts
- **Deadline:** After Epic 3 completion
- **Priority:** HIGH

### Technical Debt

#### 1. Standardize Frontend Error State Pattern
- **Owner:** Elena (Junior Dev)
- **Action:** Create reusable error state component with retry button
- **Pattern:** Error message + retry action (calls `queryClient.refetch`)
- **Priority:** MEDIUM
- **Estimated Effort:** 2 hours
- **Acceptance:** Component used in all future stories requiring error states

#### 2. Add Null Handling Checklist
- **Owner:** Charlie (Senior Dev)
- **Action:** Add to story creation workflow
- **Process:**
  1. Identify all nullable fields in schema
  2. For each nullable field, define handling strategy:
     - Fallback to default value
     - Show error state
     - Make optional and handle gracefully
- **Priority:** MEDIUM
- **Estimated Effort:** Document during next story planning (15 min)
- **Acceptance:** All Epic 3 stories explicitly address null handling in dev notes

### Team Agreements

1. **Scope First, Polish Second:** Stories must meet AC criteria before enhancements are considered. If it's not in the acceptance criteria, it shouldn't block story completion.

2. **Code Review Timeboxing:** MEDIUM issues shouldn't require more than 1 round of fixes. If more fixes are needed, reconsider severity classification.

3. **Learning Documentation:** If we fix something in code review that represents a learning opportunity, document it in `solution-patterns.yaml` for future reference.

4. **Retrospective First:** No epic is considered "fully done" until the retrospective is completed and action items are assigned.

## Lessons Learned for Epic 3

### What to Continue
1. **Use BMAD workflow** - It effectively captured and propagated learnings
2. **Code reviews** - But with clearer scoping (critical vs. enhancement)
3. **Service layer patterns** - `flush()` in service, `commit()` in router
4. **Subquery optimization** - Avoid N+1 queries with proper SQL joins

### What to Improve
1. **Null handling** - Make it part of initial implementation, not a review fix
2. **Error states** - Create reusable pattern before Epic 3 starts
3. **Scope discipline** - Meet AC criteria first, add enhancements later
4. **Retrospective practice** - Actually run them after every epic

### What to Avoid
1. **Enhancement creep in code reviews** - Keep focus on AC violations and critical issues
2. **Skipping retrospectives** - They're essential for capturing learnings
3. **Relying on reviews for basic quality** - Get it right during implementation
